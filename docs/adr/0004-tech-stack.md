# ADR 0004. Технологический стек и требования к коду

**Статус:** Accepted (2026-09-26)

## Сборка

- Gradle с Kotlin DSL (`*.kts`), **version catalog** (`gradle/libs.versions.toml`) — все версии
  только там.
- Kotlin, KSP для кодогенерации (Hilt/Dagger, Room).
- Модули: `:app` (Android) и `:fog-core` (чистый JVM) — см. ADR 0005.
- Секреты (ключ MapKit) — в `local.properties` (`MAPKIT_API_KEY=...`) → `BuildConfig`, не в
  репозитории.

## Платформа

- `minSdk = 26` (Android 8.0), `compileSdk`/`targetSdk` — актуальный стабильный API.
- MapKit — артефакт **`com.yandex.android:maps.mobile:<version>-lite`** (карта, слои, тайловый
  API, плейсмарки, слой пользователя). `full` подключается заменой одной строки в catalog,
  если понадобятся поиск/маршруты.

## Тесты

- Unit-тесты: **JUnit 5 (Jupiter)** + `kotlinx-coroutines-test` + **Turbine** для Flow.
  В `:fog-core` — нативно, в `:app` — через плагин `android-junit5`.
- Основная масса тестов — в `:fog-core` (проекция, тайловая арифметика, хранилище).
- Инструментальные тесты — точечно (сверка проекции с `map.projection()`, спайк слоя).

## UI

- **Single Activity.** Внизу — карта Яндекс MapKit как обычный `MapView` (не Compose),
  поверх — UI-слой на **Jetpack Compose**.
- **Navigation 3** (`androidx.navigation3`) для стека экранов.
- Дизайн-система — **Material 3** (`androidx.compose.material3`); основной акцентный цвет —
  **жёлтый** (primary в светлой и тёмной схемах строится от жёлтого seed-цвета).

## Асинхронность

- **Корутины и Flow.** Чистый реактивный подход: потоки иммутабельных данных вместо сырых
  колбэков. Колбэки платформы/SDK (локация, MapKit) немедленно оборачиваются в
  `callbackFlow`/`suspendCancellableCoroutine` на границе системы.

## DI

- **Dagger 2**; на начальном этапе допускается **Hilt**.
- Каждый экран имеет `ViewModel`, получающую все зависимости через DI.

## Архитектура экранов («чистая архитектура» + redux)

- Бизнес-логика экрана — в отдельных объектах **use case**.
- Внутри экрана — **redux**: состояние в `StateFlow<State>`, изменяется только функцией
  `reduce(state, action)`; наружу из `ViewModel` торчат **только** диспатчер
  `dispatch(action)` и иммутабельный `state: StateFlow<State>`; composable экрана рендерит
  `state` и отправляет `Action`'ы.
- Экраны, их composable, `State` и `Action` — в отдельных пакетах.
- **Навигация внутри redux**: реакция на некоторые `Action`'ы вызывает методы объекта-роутера,
  который хранит текущий навигационный стек; главный composable рендерит стек через
  Navigation 3.

## Данные

- **DataStore** — key-value настройки.
- **Room** — БД, когда понадобится (на начальном этапе не нужна).

## Карта

- `ViewModel` для Activity и карты может отходить от правил экранов (рендер тайлов сложнее),
  но команды принимает как `Action`, а состояние для рендера отдаёт иммутабельным view state.
- Хранилище и структура данных тумана — отдельный пакет, главный класс **`MapStorage`**:
  модификация, запросы, эффективное обновление, загрузка/сохранение на диск.
- **`MapRepository`** — высокоуровневая обёртка над `MapStorage`: кисти, линии, формирование
  массивов для чанков по запросам и т. п.
- **`LocationRepository`** — вся работа с локацией, активностью пользователя, фильтрацией
  невозможных перемещений и обновлениями. Источник — **Fused Location Provider**
  (`play-services-location`), позже — ActivityRecognition оттуда же.
- **`MapRenderer`** — весь код работы с картой: камера, плейсмарки, слои.
- **`MapFogLayerRenderer`** — рендеринг, загрузка и обновление тайлов слоя посещённых
  «пикселей».
- Все `ViewModel` и рендереры общаются с хранилищами и бизнес-логикой **только через use
  case'ы**.

## Процесс

- Вопросы по стеку задаются **до** реализации.
- Документация (ADR) — на русском; код, комментарии, идентификаторы, сообщения коммитов — на
  английском.
