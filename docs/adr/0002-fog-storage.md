# ADR 0002. Структура данных тумана войны

**Статус:** Accepted (2026-09-26)

## Контекст

Нужно хранить множество посещённых ячеек z20 (ADR 0001) так, чтобы:

- быстро отвечать на запрос «биты внутри тайла (x, y, z)» для рендера на любом зуме;
- быстро обновляться от GPS-«кисти» (десятки ячеек за фикс);
- дёшево считать прогресс (число открытых ячеек в регионе) для ачивок;
- надёжно сохраняться на диск и легко синхронизироваться/сливаться между устройствами.

Посещённое множество разреженно (пути вдоль улиц) и хорошо сжимается; объём в принципе не
проблема — дерево нужно прежде всего для скорости рендера низких зумов и счётчиков.

## Решение

### Ключи

Любой тайл/ячейка пирамиды кодируется одним `Long`:

```
key = (z shl 58) or morton(x, y)     // morton — чередование бит x и y (quadkey)
```

Свойство quadkey: ключ родителя — префикс ключа потомка, поэтому «все чанки внутри тайла T» —
это range-scan по диапазону ключей.

### Чанки

Единица хранения — **чанк = тайл зума `Zk = Zs − 8 = 12`**, содержащий 256×256 = 65 536 бит
ячеек z20 (8 КБ raw). В Москве чанк ≈ 5.5 × 5.5 км.

```
Chunk(key, words: LongArray[1024], visitedCount: Int)   // иммутабельный снапшот, copy-on-write
```

- Чанк — **иммутабельный снапшот**; запись создаёт новый чанк (копия 8 КБ). Читатели
  (рендер тайлов в фоновых потоках MapKit) работают без блокировок.
- `FULL` (`visitedCount == 65536`) — на диске биты не хранятся.
- Блочные суммы внутри чанка (нужны для тайлов зума `Zk..Zs`) **не хранятся**, а считаются
  из бит на лету (`countInBlock`: ≤ 1024 `popcount` на чанк, блоки выровнены по степени двойки и
  не пересекают границ 64-битных слов). Хранить mip-пирамиду невыгодно: она в ~10 раз больше
  самих бит, а число существующих чанков в любом тайле мало.

### Агрегаты над чанками

Для всех `z < Zk` хранится `agg(key) = число открытых ячеек z20 внутри тайла` («summed
quadtree»). Запись обновляет ≤ 12 строк по пути к корню. Тайл зума `z < Zk` рендерится
только из агрегатов (плотность → прозрачность), не трогая биты.

### Операции `MapStorage` (примитивы)

- `isVisited(cell)`, `markVisited(cells): ChangeSet` — только установка (снятие бита в игре
  не предусмотрено).
- `chunk(key)`, `chunksWithin(tile)` — снапшоты чанков; для `z < Zk` — range-scan по quadkey.
- `visitedCount(tile)` на любом зуме: `z ≤ Zk` — из агрегатов, `Zk < z < Zs` — блочная сумма в
  чанке, `z ≥ Zs` — бит ячейки.
- Поток изменений `changes: SharedFlow<ChangeSet>` (затронутые чанки, число новых ячеек) для
  инвалидации рендера и прогресса.
- `load()` / `flush()` — блокирующие операции с `ChunkStore`; вызываются с IO-диспетчера.
- `clear()` — полный сброс (кнопка «Очистить исследованное» в настройках, 2026-09-26): удаляет
  файлы чанков и очищает память и агрегаты. Блокирующая; сериализована с `flush()`, чтобы
  запись, начатая до сброса, не вернула удалённые чанки. Если файлы удалить не удалось, в
  памяти ничего не стирается, а все чанки помечаются грязными, чтобы следующий `flush()`
  восстановил уже удалённые файлы.
- Чтения конкурентны и без блокировок, запись сериализована.

Формирование массивов покрытия для тайлов (свёртка z20 → z18, сетки плотности) — уровень
`MapRepository`, поверх этих примитивов.

### Персистентность (v0)

Room на старте не нужен (ADR 0004). `MapStorage` сам сохраняет чанки на диск:

- каталог `files/fog/`, один файл на чанк: `<key>.chunk` — заголовок (версия формата, key,
  state, popcount) + deflate-сжатая битовая карта;
- запись write-behind: грязные чанки сбрасываются с задержкой и при уходе в фон, атомарно
  (temp → rename);
- агрегаты и mip восстанавливаются из чанков при загрузке (тысячи чанков — доли секунды),
  т.е. на диске лежит единственный источник истины — биты.

Позже (когда появятся индексы/запросы) файлы можно заменить или дополнить Room без изменения
API `MapStorage`.

### Синхронизация

Чанк — естественная единица синхронизации и бэкапа; слияние с другого устройства — побитовое
OR, коммутативно и идемпотентно. Полный сброс в OR не выражается: при появлении синхронизации
его нужно передавать отдельным событием (например, номером «эпохи», с которым сливаются
только чанки той же эпохи).

## Оценки

- Москва внутри МКАД (~880 км²) на z20 ≈ 1.9 млн ячеек = 240 КБ raw при полном покрытии;
  реальное посещённое множество — единицы процентов и сжимается в 5–10×.
- Игрок с 10 000 км пути и кистью 50 м → ~1 млн ячеек z20 ≈ 130 КБ бит.

## Последствия

- Рендер любого тайла — O(размер тайла), без перебора посещённых ячеек.
- Формат файла чанка — публичный контракт, версионируется с первого байта.
- Отмена/удаление отдельных посещений не поддерживается по дизайну (упрощает слияние и
  агрегаты); стереть можно только всё сразу (`clear()`).
